# Data collection process (going forward)

This is the process for getting new PPI program activity into the
dashboard without repeating the mess this project spent most of its effort
cleaning up: unmerged school-name spelling variants, undefined Karatu 23
additions, activities missing entirely for a year (2024), and schools that
sit in limbo for years without a clear status (Gyekrum Arusha, Kainam).

The short version: **log every site visit/activity as one row in a shared
spreadsheet using the canonical school list, export it to
`data/activity-log.csv` periodically, and rebuild.** No one needs to touch
the original xlsx or understand its quirks going forward.

## Why a new file instead of editing the xlsx

`Implementation_Timeline_for_Website_2007-2025.xlsx` is a historical
archive extract, not a living form — its "By Date" sheet has years of
inconsistent formatting that `build_program_data.py` already has to work
around (see `data/school-taxonomy.yml`). Every new entry added to it inherits
that risk. `data/activity-log.csv` is a plain, append-only table with a
fixed schema, built for the pipeline's validation (duplicate-name detection,
required-field checks) from day one — see `test_activity_log_*` in
`tests/test_program_data.py` for exactly what's enforced.

## Step 1 — Set up the shared log (one-time)

Recommended: a Google Sheet that mirrors `data/activity-log.csv`'s columns
exactly, so exporting it is a straight copy-paste or File > Download > CSV.
This is easier for non-technical field staff than editing a CSV/git
directly, supports offline use via the Sheets app, and can use **data
validation dropdowns** so people select a school instead of typing it
(exactly what prevents the next "Banjika" vs "Banjika" typo).

1. Create a Google Sheet with these columns, in this order:

   | Year | Month | Implementation | School | District | Country | Notes | EnteredBy | EntryDate |
   |---|---|---|---|---|---|---|---|---|

2. Add a **data validation dropdown** on the `School` column sourced from
   `canonical-schools.csv` (regenerated by every `build_program_data.py`
   run, in this same folder) — paste its `canonicalName` column as the
   dropdown's list of options. This is the single biggest thing that
   prevents future name-variant cleanup work.
   - If the school genuinely isn't on the list yet (new site), see "Adding
     a new school" below before logging its first activity.
3. Share edit access with whoever logs activities; share view access with
   the board.

## Step 2 — Log every activity, one row per visit

Fill in a row **every time** something happens at a school: an install, an
upgrade, a training session (including follow-ups), or a Shule Direct
content update. Required fields:

- **Year** — numeric, e.g. `2026`.
- **Month** — free text, e.g. `June` (doesn't need to be a specific format,
  but be consistent).
- **Implementation** — a short description of what happened. **Use these
  keywords deliberately** — `build_program_data.py` classifies the
  activity type and equipment generation by matching words in this field:
  - Contains `train` or `workshop` -> classified as **training** (per AJ's
    Key tab: training is an activity on an existing site, never +1 school).
  - Contains `Shule Direct` (with `train`) -> **training**; without
    `train` -> **content**.
  - Contains `upgrade` or `replace missing` -> **upgrade**.
  - Contains `phase`, `sparc`, `pi-oneer`/`pioneer`, `solar`, `laptop`,
    `computer`, `rachel`, or `network` -> **deploy**.
  - Also include the generation name if applicable (`SPARC+`, `SPARC`,
    `Pi-oneer`, `Phase 1`, `Phase 2`) so it's picked up automatically —
    e.g. `"SPARC+ Installation"`, not just `"Installation"`.
  - Anything that doesn't match a keyword above is filed as **other** —
    fine occasionally, but if you're logging the same kind of activity
    repeatedly under "other", tell Charlie so a new keyword can be added.
- **School** — pick from the dropdown (canonical name). Don't type a new
  spelling of an existing school.
- **District**, **Country** — usually the same for a given school every
  time; fill them in on a school's first-ever row at minimum.

Optional but encouraged:
- **Notes** — anything a board member would want to know (trainer name,
  attendee count, issues found, follow-up needed). Shows up on the
  school's record in the dashboard.
- **EnteredBy**, **EntryDate** — who logged it and when, for audit trail.

**Example row:**

```
2026,June,Training - Follow-up visit,Banjika,Karatu,Tanzania,Refresher training for 3 teachers on Shule Direct,Field Officer,2026-06-15
```

## Step 3 — Adding a new school

Don't just start logging activities for a school that isn't in the
canonical list yet — that's exactly how Gyekrum Arusha and Kainam ended up
sitting in an ambiguous state for years. Before its first log entry:

1. Confirm the school name spelling with whoever ran the visit.
2. Decide with AJ Poole: is this school part of the Karatu 23? A different
   program entirely? What cluster?
3. If it's a Karatu 23 addition, add it to the appropriate list
   (`kdp1_named` or `kdp2_named`) in `data/school-taxonomy.yml`, with a
   `reason` and `confirmed_by: AJ Poole` (see that file's own comments and
   `CONTRIBUTING.md`'s "Making a data change" section).
4. If it's a new school outside the current taxonomy's special cases (not
   Karatu, not Zanzibar), no taxonomy edit is required — the pipeline will
   pick it up automatically from its first `activity-log.csv` row and file
   it under a district-based cluster. Just make sure its name is spelled
   consistently from day one so it doesn't need a later alias.
5. Only after this, log its first activity and add it to the Google
   Sheet's dropdown list source (or just re-paste the updated
   `canonical-schools.csv` after the next rebuild — it will include the
   new school automatically once it's appeared in a build).

## Step 4 — Export and rebuild

On a regular cadence (recommended: monthly, and always before a board
meeting):

1. Export the Google Sheet: File > Download > Comma-separated values
   (.csv), or copy/paste its rows into `data/activity-log.csv` directly
   (keep the same header row).
2. From `powering-potential-dashboard/`:
   ```bash
   pip install -r requirements.txt
   python3 build_program_data.py
   ```
   This will **fail loudly** (not silently produce bad data) if:
   - A logged school name looks like an unmerged spelling variant of an
     existing one (the same duplicate-name gate that protects the xlsx).
   - A row is missing its School or Implementation value.
   - The Year column has something non-numeric in it.
   Fix the flagged row in the Google Sheet (and re-export), or add a
   taxonomy alias if it's a genuine new spelling, then re-run.
3. Run the tests:
   ```bash
   python3 -m pytest tests/ -v
   ```
4. Regenerate the combined bundle if you also touched any UI files:
   ```bash
   python3 assemble_index.py
   ```
5. Commit `data/activity-log.csv`, `program-data.js`, and
   `canonical-schools.csv` together, and publish per `CONTRIBUTING.md`.

## What this does and doesn't solve

- **Solves**: the specific failure modes seen in the archive — unmerged
  name variants, missing years, and schools with no clear classification —
  by making logging structured and validated from the start, instead of
  cleaned up years later.
- **Doesn't solve**: this is still a manual export-and-rebuild process, not
  a live sync. If that becomes a bottleneck, a follow-up could wire the
  Google Sheet directly to a scheduled GitHub Action (Google Sheets API ->
  CSV -> automatic PR, similar in spirit to
  `.github/workflows/sync-powering-potential-dashboard.yml`) instead of a
  manual export. Worth doing once this manual process has been used for a
  few cycles and the column schema has proven stable.
- **Cross-repo note**: like the rest of this dashboard's pipeline, this
  process currently lives in `wilsonck75.github.io` (see `CONTRIBUTING.md`,
  "Access limitation"). If `D-Cubed-Data-Lab` becomes writable again, this
  file and `data/activity-log.csv` should move there so there's one source
  of truth for both the historical archive and the ongoing log.
